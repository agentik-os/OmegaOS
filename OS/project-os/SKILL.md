# Project {OS}

Scope a project so it can be finished, track it so the truth arrives in time to
act, and land it so it is genuinely over.

## When to use this

Use it when the work has a start, an end and a deliverable, spans more than a
few days, and involves more than one moving part or more than one person.

Typical openings: I need to deliver this by the end of the month, this thing
has been going on for weeks and I cannot tell if it is nearly done, the client
keeps adding things, we said six weeks and we are in week nine.

Near neighbours it is confused with:

| If the real need is | The right OS is |
|---|---|
| what to do today, and proof it happened | Execution {OS} |
| what the software should be, and how it gets built | Blueprint, Stepper, Builder {OS} |
| managing the client, not the work | Client {OS} |
| who does it and how it is briefed | Team & Delegation {OS} |
| the recurring operating process, not a one-off | Operations {OS} and Process & SOP {OS} |
| approval of a change that crosses a policy boundary | Review & Governance {OS} |

## Capabilities

- Force a done test before any planning, and refuse to plan without one.
- Write a scope statement with an explicit out-of-scope list.
- Build a milestone plan with owners, dates, dependencies and a named critical
  path.
- Report status as position against plan, with the slip and the next decision
  due, never as a list of activity.
- Price a scope change in time, money and landing date before anyone decides.
- Maintain a risk register where each risk has a trigger and a response, not a
  severity adjective.
- Present the recovery option set when a project is late: cut scope, extend,
  add capacity, or stop.
- Run the closeout: acceptance, what shipped, what was cut, actual versus
  planned, and the estimate correction for next time.

## Procedure

1. Identify the requester and what changes for them when this exists.
2. Write the done test. Observable, checkable by someone else. Stop here if it
   cannot be written.
3. Write the out-of-scope list. It is usually longer than the scope list.
4. Collect hard constraints: dates, budget, people, external dependencies.
5. Decompose to milestones. Each gets one owner, one date, one acceptance test.
6. Map dependencies and name the critical path.
7. Sanity-check against real capacity and against how long comparable work
   actually took. Label every date with its basis.
8. Emit next actions to Execution {OS} and work packages to Team & Delegation
   {OS}.
9. On a fixed cadence, report position: milestone, slip, blocker, next decision.
10. On any change, open a change record and price it before deciding.
11. When the done test is met, run acceptance and the closeout. When it will not
    be met, present the recovery options, including stop.

## Handoffs

| Send to | What | What they expect |
|---|---|---|
| Execution {OS} | next actions with deadlines | one physical next action per item |
| Team & Delegation {OS} | assignable work packages | outcome, definition of done, constraints, authority level |
| Client {OS} | status and change requests | facts and dates, in the client's language |
| Meeting {OS} | a decision that needs a room | the decision, the options, the decider |
| Documentation {OS} | the closeout record | the artifact, its topic, its owner and review date |
| Review & Governance {OS} | changes above threshold, and the project retro | evidence, the change record, the decision requested |
| Context & Memory {OS} | actual versus planned durations | confirmed numbers, so the next estimate is better |
