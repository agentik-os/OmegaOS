# Brand {OS}

Identity, voice and the visual system that carries them.

## When to use this

Use this OS when the question is **how does the claim sound and look, everywhere
a stranger meets it**. Concretely: establishing an identity, naming a company or
a product, writing voice rules that can actually reject a sentence, building the
type, colour and spacing system, auditing a draft or a screen against that
system, releasing assets, or evolving the system when it stops fitting.

Near neighbours it is confused with:

- **Positioning {OS}** decides the claim and the category. Brand expresses
  them. If the argument is about what is true, that is Positioning.
- **Content {OS}** decides what to publish, to whom and when. Brand decides how
  it must sound and look. Brand never sets editorial strategy.
- **Design {OS}** decides product interface and interaction. Brand hands Design
  the visual system; Design decides how a screen behaves.
- **Storyteller {OS}** decides narrative structure, truth and consent. Brand
  supplies the voice rules a story may not contradict, and nothing more.
- **Marketing execution** produces campaigns. Brand judges them against the
  system and does not commission them.

The discriminating question: **would this decision change what we are claiming,
or only how it is expressed?** If it changes the claim, stop and go to
Positioning {OS}. If it changes the expression, this is the OS.

## Capabilities

- Derive the identity core (register, archetype, promise) from the claim and
  the audience register, never from taste alone.
- Name a company, product or feature, and test the name against the claim, the
  category and the audience register.
- Write voice rules as falsifiable pairs: one sentence accepted, one refused.
- Build the visual system: type scale, colour ramps with contrast values,
  spacing scale, imagery direction and logo usage rules.
- Emit the system as machine readable tokens that a real surface consumes.
- Audit any artifact rule by rule and cite the offending sentence, value or crop.
- Maintain the asset library with usage rules and allowed surfaces per asset.
- Version an evolution and produce the migration list of every affected surface.

## Procedure

1. Read the positioning statement, the claim ledger and the exclusion. If there
   is no claim on record, stop and name Positioning {OS} as the blocker.
2. Read the audience register from Customer Discovery {OS}: the vocabulary the
   audience uses, and what already reads to them as marketing.
3. Inventory what exists: the site, the deck, the last twenty published pieces,
   the product interface. The system starts from artifacts, not from a blank
   page.
4. Establish the identity core. Every element traces back to the claim or the
   register, and any element that traces to neither is cut.
5. Write voice rules. For each rule, produce the sentence it accepts and the
   sentence it refuses; drop any rule that cannot refuse a real sentence.
6. Build the visual system, then express it as tokens with contrast and size
   constraints checked. A value that fails accessibility fails the token.
7. Audit the existing inventory from step 3 against the new system, and produce
   the list of what is off system today.
8. Publish the brand system with a version number, and hand the tokens to
   Design {OS} and the voice rules to Content {OS} and Storyteller {OS}.
9. Run `AUDIT` on every artifact before release. A failure is a failure, and
   shipping anyway requires a named approver and a recorded reason.
10. On evolution, version the change and produce the migration list. Close the
    version only when every listed surface is corrected or explicitly waived.

## Handoffs

- **Design {OS}** receives the visual system and the tokens for product
  surfaces. It expects machine readable values with their accessibility
  constraints, and a rule for what it may extend versus what it must not
  reinterpret.
- **Content {OS}** receives the voice rules and the visual system for editorial
  surfaces. It expects rules that can reject a draft mechanically, and it owns
  what gets published, not Brand.
- **Storyteller {OS}** receives the voice rules a story may not contradict. It
  expects rules about register and vocabulary, not instructions about structure
  or truth, which are its own.
- **Sales {OS}** receives the brand system and voice rules for decks, proposals
  and outbound. It expects templates it can fill without breaking the system.
- **Offer {OS}** receives the brand system for how an offer is presented. It
  expects naming conventions for products, tiers and features.
- **Affiliate {OS}** receives the brand system and the asset release rules. It
  expects to know exactly which assets a partner may use and on which surfaces,
  because every third party release is an approval boundary.
