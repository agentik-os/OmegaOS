# Offer {OS}

The thing you sell, shaped so the value is obvious.

## When to use this

Use Offer {OS} when the question is **what does the customer actually
receive**: drafting a new offer, drawing the line between what is included and
what is not, designing a guarantee, assembling the proof behind a promise,
stress testing an offer against the objections it will really meet, or
retiring an offer that still has paying customers on it.

Near neighbours it is confused with:

- **Pricing {OS}** owns what you charge. If the sentence contains a number, a
  tier, a discount or a payment term, it is Pricing.
- **Positioning {OS}** owns the category and the claim. If the question is who
  this is for and why you rather than the alternative, it is Positioning.
- **Sales {OS}** owns the conversation and the close. If the question is how
  to move this specific prospect forward, it is Sales.
- **Delivery & Customer Success {OS}** owns fulfilment. If the question is how
  the work actually gets done and whether the customer succeeded, it is
  Delivery.

The discriminating question: **is this about what is promised, or about what
it costs, who it is for, or how it is delivered?** Only the first is Offer.

## Capabilities

- Draft an offer from a positioning claim and a named job to be done.
- Convert a vague promise into a named outcome the buyer can recognise.
- Draw a scope boundary and force at least one explicit exclusion.
- Give every deliverable an acceptance form Delivery can check against.
- Design a guarantee and model its worst case cost before it is published.
- Assemble a proof set where every proof item carries a source.
- Reconcile the offer against the fulfilment cost model from Delivery.
- Stress test the offer against real objections and log the revisions forced.
- Version a live offer and keep the obligation attached to the version sold.
- Retire an offer with a migration destination for every live customer.

## Procedure

1. Read the positioning statement and the claim ledger. If either is missing,
   stop and name Positioning {OS} as the blocking unit.
2. Read the job to be done from Customer Discovery {OS} and the demand
   evidence from Validation {OS}.
3. Draft the promise as an outcome, not an activity. Reject any wording whose
   subject is the seller's effort rather than the buyer's result.
4. Enumerate the deliverables. Give each one an acceptance form: a condition
   under which it is done, checkable without a conversation.
5. Draw the scope boundary and write the exclusions. An offer leaves this step
   only with at least one exclusion stated.
6. Design the guarantee. Model the worst case cost, not the expected case, and
   write the ceiling above which it is withdrawn from new sales.
7. Pull the fulfilment cost model from Delivery & Customer Success {OS} and
   compare it against the offer economics. A gap freezes the offer.
8. Assemble the proof set. Remove any proof item that cannot name its source.
9. Stress test against real objections. Answer each one, or change the offer.
10. Present the exact wording for human approval, then publish, version and
    emit to the consuming units.

## Handoffs

- **Pricing {OS}** receives the offer definition. It expects a stable set of
  deliverables and a scope boundary, because it cannot price a shape that is
  still moving.
- **Sales {OS}** receives the offer definition plus the scope boundary and
  guarantee. It expects to be able to answer in scope or out of scope for any
  specific request, without escalating.
- **Delivery & Customer Success {OS}** receives the scope boundary and the
  guarantee. It expects every promise to be checkable against that boundary,
  and it returns the fulfilment cost model that Offer consumes.
- **Revenue {OS}** receives the offer definition so a closed contract can be
  reconciled against what was actually sold.
- **Content {OS}** receives the offer definition as the thing the content
  points at. It expects approved wording, not drafts.
