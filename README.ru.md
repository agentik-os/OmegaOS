# OmegaOS

Терминальный control plane для параллельного управления флотом ИИ-агентов, пишущих код, — где каждый агент подчиняется одному и тому же типизированному своду правил.

[![CI](https://github.com/agentik-os/OmegaOS/actions/workflows/ci.yml/badge.svg)](https://github.com/agentik-os/OmegaOS/actions/workflows/ci.yml) ![License: MIT OR Apache-2.0](https://img.shields.io/badge/license-MIT%20OR%20Apache--2.0-blue.svg) ![Built with Rust](https://img.shields.io/badge/built%20with-Rust-orange.svg)

OmegaOS — это не библиотека, которую вы импортируете. Вы ставите её на Linux-машину и получаете команду `omega`, TUI для наблюдения за сессиями и их завершения, слой оркестрации, который раздаёт работу агентам, и мост в Telegram для управления с телефона. Новые сессии по умолчанию используют OpenAI Codex. Claude Code, Gemini, Pi, Hermes и GLM остаются явными вариантами. Каждый агент получает компактный типизированный контекст политик для своей роли, скомпилированный из одной доктрины.

Текущая версия — см. [CHANGELOG.md](CHANGELOG.md) (`omega -V` на установленной машине). Я гоняю её каждый день; будьте готовы к шероховатостям.

## Установка

Одна команда на Linux-машине (на macOS в основном работает):

```
npx omega-os
```

Она клонирует репозиторий и запускает установщик за интерактивным экраном прогресса с матричным дождём (печатайте, чтобы подсыпать глифов, `space` — импульс; `npx omega-os --plain` даёт обычную полоску). Если хочется руками:

```
git clone https://github.com/agentik-os/OmegaOS
cd OmegaOS
./install.sh
```

Установщик скачивает готовые бинарники `rmux` + `omega` под вашу платформу, когда для неё опубликован релиз (с проверкой по контрольной сумме), а иначе откатывается на сборку из исходников — так что свежий клон всегда воспроизводит систему, просто быстрее, когда бинарник есть. Принудительная сборка из исходников — `OMEGA_FROM_SOURCE=1 ./install.sh`.

## Обновление

```
omega update           # fetch + fast-forward + переустановка
omega update --check   # что изменится? (ничего не трогает)
```

Оно обновляет тот чекаут, который найдёт (`$OMEGA_SRC`, текущий каталог, затем
`~/Station/SideBusiness/OmegaOS`, `~/Station/OmegaOS`, `~/OmegaOS` — либо передайте
`--dir`), пересобирает из исходников и заново прогоняет установщик. Ваше состояние
в `~/.omega` сохраняется: секреты, проекты, конфиг Telegram и `config.toml` никогда
не перезаписываются.

Если в чекауте есть локальные изменения или незапушенные коммиты, обновление
**останавливается и говорит вам об этом**, а не трогает вашу работу — закоммитьте,
спрячьте в stash или запушьте, а потом запустите его заново.

Оно ещё и само держит себя в актуальном состоянии: каждая установка проверяет
обновления ежедневно в 03:30 и ставит то, что найдёт, пропуская любую ночь, когда
в вашем чекауте есть локальная работа, агент в середине хода или один и тот же
коммит уже падал три раза. Автоустановка означает доверие к репозиторию каждую
ночь, поэтому переключатель — одна команда:

```
omega config set auto_update check   # сообщать мне, а не ставить
omega config set auto_update off     # вообще ничего не делать
```

## Первые 5 минут

Стек ставит себя сам; остаётся только личное. **`omega guide` печатает полный
пошаговый разбор** (он же сохраняется в `~/.omega/GETTING-STARTED.md` и
показывается в конце установки). Коротко:

1. **Подключите Codex** *(обязательно для среды исполнения по умолчанию)*: выполните `codex login`, затем проверьте через `codex login status`. Claude остаётся опциональным — через `claude` и `/login`.
2. **Управление из Telegram** *(рекомендуется)* — токен у [@BotFather](https://t.me/BotFather), ваш id у [@userinfobot](https://t.me/userinfobot), дальше `OMEGA_TG_TOKEN=<TOKEN> omega telegram setup <ID> --user-id <ID>` (форма с переменной окружения держит токен вне списка процессов). Чтобы на каждый проект был свой топик: группа + включённые Topics + бот-админ → `/setupgroup` → `/sync`.
3. **Ключи сервисов** *(опционально)* — `~/.omega/provisioning/services.env` (Vercel / GitHub / Convex / Stripe / OpenAI для голоса) обеспечивает автопровижининг новых приложений.
4. **Добавьте проект** — `omega` → **[N] New Project**, Telegram → *Import from GitHub*, или просто положите репозиторий в `~/Station/<Category>/`.
5. **Проверьте** — `omega doctor`: каждая строка `[+]`.

## Что вы можете делать

- **Отправлять миссии.** `omega dispatch <Project> "<mission>"` передаёт работу оракулу этого проекта, а тот планирует, порождает воркеров и прогоняет результат через gate. `omega orchestrate` запускает весь конвейер классификация → план → отправка → наблюдение → gate одной командой.
- **Гонять типизированные планы.** `/omg-planner` раскладывает сборку в типизированный DAG (`.planner/tracker.json`); `omega plan-run` исполняет его со структурной защитой от пропуска шагов (Gate) и независимым доказательством через verify-команду (Guardian).
- **Поднимать приложения целиком.** `/omg-new-project` провижинит Vercel/Convex/GitHub/Clerk/Stripe из ваших ключей, разворачивает стек, а дальше идёт vision → PRD → план → сборка.
- **Безопасно параллелить.** Воркеры захватывают свои файлы настоящими рекомендательными блокировками (`fs2`), а `omega spawn-worker --worktree` даёт каждому параллельному воркеру собственный git-worktree с чистым merge в конце. Сигнал о завершении создаёт результат-кандидат. Закрыть его могут только независимый верификатор и приёмочный gate миссии.
- **Аудировать всё.** Quality Arsenal из 23 форензик-аудитов Gestalt-Popper (`codeaudit`, `secaudit`, `perfaudit`, `a11yaudit`, …), которые подбираются автоматически под то, что изменилось, плюс `/omg-acceptance` — автономный приёмочный gate в браузере, который обходит все маршруты и чинит найденное.
- **Созывать совет.** `/omg-llm-council` задаёт один вопрос четырём разным моделям Claude параллельно, заставляет их анонимно отрецензировать друг друга и сводит всё в вердикт, не пряча особые мнения, — без API-ключей, всё крутится внутри вашей текущей сессии.
- **Ходить по вебу агентно.** `/omg-browser-use` рулит облачным браузером для задач, которые не выразить скриптом Playwright.
- **Делать и go-to-market.** Встроенный маркетинговый набор (исследование рынка, позиционирование, контент-стратегия, соцсети, cold email, рекламные креативы, стратегия запуска) плюс пара скиллов Higgsfield для визуальной идентичности.
- **Получать отчёты на телефон.** Каждая миссия заканчивается брендированным PDF-отчётом в Telegram-топике проекта, а пока она идёт, карточка прогресса обновляется на месте. Бот-депозит даёт агентам приватный входящий ящик для файлов, которые вы шлёте с телефона.
- **Управлять всем этим.** `omega doctor` (здоровье всего стека), `patrol` (сторож сессий), `usage` (бюджет токенов + алерты в Telegram), `backup` (невоспроизводимое состояние `~/.omega` → один tgz), `cleanup` / `kill-all`, `timeline` (проиграть миссию заново), `resurrect` (поднять упавшего оракула), `provision` (группы учётных данных под каждого клиента).
- **Закрывать тикеты Linear от начала до конца.** `/omg-linear` чинит, снимает доказательства, аудирует до 100/100, комментирует и переводит тикет в ревью — но никогда в Done; это делает человек. См. [Интеграция с Linear](#интеграция-с-linear).

Три пути внутрь: TUI на `ratatui` (5 вкладок: Sessions, Menu, Agentic, Settings, Help), CLI `omega` (40+ команд) и хаб в Telegram. Режим RPC (JSONL через stdin/stdout) позволяет рулить всем этим из других инструментов. Под капотом всё крутится на [rmux](https://github.com/agentik-os/rmux), терминальном мультиплексоре на Rust, — зависимости от tmux нет.

## Доктрина

Есть типизированный реестр из 7 Законов и 47 именованных операционных Правил. `omega rules list` печатает актуальный набор. Компилятор живёт в `crates/omega-core/src/rules.rs`; он выдаёт детерминированный контекст с учётом провайдера и жёстким бюджетом OmegaOS в 24 КБ.

**Законы нерушимы.** Они связывают каждого агента и стоят выше любого правила и любой задачи. Их семь:

- **L0 — Отгружай правду.** Изменение не готово, пока чистая пересборка его не воспроизведёт и оно не запушено. Всё, что меньше этого, — черновик.
- **L1 — Runtime — единственная правда.** Код и комментарии заявляют намерение. Только запуск показывает реальность. Когда они расходятся, побеждает runtime.
- **L2 — Исследователь, а не подхалим.** Оспаривай ошибочную посылку с аргументами, прежде чем действовать. Никакой фальшивой уверенности. «Должно сработать» без доказательств — это ложь.
- **L3 — Решай и действуй.** Отправленный на задачу агент автономен. Он никогда не останавливается, чтобы спросить «продолжать?». Он решает, выполняет и докладывает потом.
- **L4 — Готово — значит 100% и проверено.** 92% — это не готово. Перечисли задачи, доведи каждую до конца, проверь каждую по runtime.
- **L5 — Качество важнее скорости.** Никаких облегчённых, урезанных или быстрых вариантов настоящего протокола. 403 или 401 — это аварийная остановка, а не пройденная проверка.
- **L6 — Доводи миссию до конца.** Перечисли, выполни, проверь и отчитайся по каждому запрошенному результату. План или частичная фаза не является допустимой остановкой.

**Правила операционные.** Именованные (R-SCOPE, R-VERIFY, R-CITE, …), разнесены по категориям Universal, QualityGate, Orchestration, Reporting и Safety. Каждое Правило ограничено теми ролями, которые оно связывает: Master, Oracle, Worker. Воркера не нагружают правилами оркестрации, по которым он всё равно ничего не сделает, а оракул не тащит на себе воркерскую дисциплину блокировки файлов. Реестр один, срезы разные.

### Воронка

Вот сам механизм. `rules::compile_rule_context_for_provider` собирает воедино компактное ядро Законов, контракт роли, правила, релевантные миссии, механику провайдера и ссылки на скиллы. Вывод сверх бюджета контекста отклоняется, а не обрезается молча. У каждого скомпилированного контекста есть детерминированный дайджест — чтобы ловить дрейф.

Воркер на три уровня ниже по дереву несёт те же семь Законов, что и Master. Операционные процедуры подгружаются, только когда их требуют роль, миссия, риск и провайдер. Так инварианты остаются универсальными, а в каждый ход не впрыскивается весь свод инструкций.


## Архитектура

Четыре уровня, сверху вниз:

```
┌─────────────────────────────────────────────────────────────────┐
│  Уровень 1 — интерфейс для человека                             │
│  TUI (5 вкладок) · CLI (40+ команд) · хаб Telegram              │
│                      ↓ намерение                                │
├─────────────────────────────────────────────────────────────────┤
│  Уровень 2 — Master (постоянный мозг — топик Atlas)             │
│  14 шаблонов агентов «Матрицы», классификация → маршрутизация   │
│                      ↓ отправка                                 │
├─────────────────────────────────────────────────────────────────┤
│  Уровень 3 — Oracle (1 на проект)                               │
│  Классификация → План → Отправка воркеров → Quality gate        │
│                      ↓ декомпозиция                             │
├─────────────────────────────────────────────────────────────────┤
│  Уровень 4 — воркеры (эфемерные, параллельные, скоуп по файлам) │
│  Выполнение → Проверка → done.json → приёмка Oracle → закрытие  │
└─────────────────────────────────────────────────────────────────┘
```

**Уровень 2 — Master.** Постоянно работающий агент, который остаётся запущенным, сам перезапускается, если падает, и возобновляет собственный диалог. Он несёт 14 шаблонов агентов, названных в честь персонажей «Матрицы» (Oracle, Morpheus, Seraph, Keymaker, Smith, Niobe, Architect, Merovingian, Neo, Zion, Link, Construct, Pythia, Council). Master — это диспетчер. Он только классифицирует и маршрутизирует работу к оракулам.

**Уровень 3 — Oracle.** По одному на проект. Он классифицирует запрос, планирует, отправляет воркеров на задачи и под конец прогоняет quality gate. Оракул оркеструет. Сам он код проекта не правит, так что тот, кто выставляет оценку, и тот, кто писал код, — никогда не один и тот же агент.

**Уровень 4 — воркеры.** Эфемерные. Они работают параллельно, и каждый ограничен своими файлами через захват файловой блокировки (рекомендательные блокировки через `fs2`) — а при желании ещё и собственным git-worktree. О завершении воркер сигнализирует, записав `done.json` со статусом `done_clean`, `pending` или `failed`; без этого статуса работа не считается готовой.

### Как проходит миссия

Запрос приходит через TUI, через CLI или через Telegram. Откуда бы он ни стартовал, он попадает на Master, который читает его, классифицирует и направляет тому оракулу, которому принадлежит соответствующий проект. Оракул планирует миссию, разбивает её на задачи и отправляет по воркеру на каждую задачу. Воркеры проверяют свои результаты по реальному runtime и пишут `done.json`; оракул читает его, прогоняет gate и рапортует выше по цепочке.

Воркеру не обязательно прогрызать свои подзадачи по одной. Он может запустить Workflow прямо в своём процессе: породить параллельных субагентов, проверить их выводы и свести их в один ответ. Так работает ревью кода, так же — исследования, аудиты и работа над дизайном.

Проверка намеренно состязательна: воркер, отрапортовавший «done», проверку не закрывает — его заявление уходит к независимым агентам и выживает, только если с ним согласно большинство (двое из трёх). Аудиты Quality Arsenal подключаются именно здесь, на этом gate.

Всё это держится на воронке доктрины, описанной выше: каждому агенту на каждом уровне в момент отправки впрыскиваются Законы и Правила, отобранные под его роль.

Этот раздел README сам по себе — пример. Его сделал Workflow. Один агент написал черновик, независимые читатели прошлись по нему в поисках текста с привкусом ИИ, другой агент переписал его с учётом помеченного, а перевод взяли на себя носители языка. Так что ни одна часть этого текста не вышла из-под единственного непроверенного прохода.

## Стек

Это Rust-воркспейс из трёх крейтов:

- `omega-core` — оркестрация, реестр правил, doctor, timeline, cleanup, patrol, блокировка файловых областей.
- `omega-cli` — бинарник `omega`, построенный на `clap`.
- `omega-tui` — менеджер сессий, построенный на `ratatui`.

Под капотом всё крутится на [rmux](https://github.com/agentik-os/rmux), терминальном мультиплексоре на Rust: демон, типизированный SDK и работа с PTY. rmux — это типизированная Rust-библиотека, поэтому OmegaOS вызывает её напрямую, вместо того чтобы дёргать tmux через шелл и парсить текст. Зависимости от tmux нет нигде.

Bun и TypeScript отвечают за рендеринг PDF-отчётов (через Next.js и Playwright) и за Telegram-ботов. Bash всплывает ровно в одном месте: в бутстрапе установки.

## Подключение удалённо

Демон rmux владеет каждой сессией, поэтому ваши агенты продолжают работать после того, как вы отключились. Чтобы вернуться к ним, сделайте **attach** — подключите терминал обратно к уже запущенной сессии:

```
rmux attach              # вернуться в последнюю сессию
rmux attach -t claude-1  # подключиться к конкретной
rmux list-sessions       # посмотреть, что живо
```

Отсоединиться обратно — `Ctrl-b d`: сессия и её агенты продолжают работать без вас.

`omega` оборачивает те точки входа, к которым вы реально тянетесь:

```
omega                       # открыть TUI-менеджер сессий (смотреть / запускать / следить)
omega attach -t claude-1    # сразу провалиться в одну сессию и работать в ней
omega master                # перейти в сессию Master
omega list                  # перечислить все живые сессии
```

Меню (`omega`) — чтобы управлять и запускать; прямой attach (`omega attach -t …` или `rmux attach -t …`) — когда хочется уткнуться в одну сессию и печатать: превью в меню *зеркалит* панель, а прямой attach даёт минимальную задержку.

По SSH с ноутбука обычный SSH ждёт полный сетевой round-trip, прежде чем отобразить каждое нажатие, так что на далёкой машине печатать тормозно, а вывод агентов приходит рывками — и неважно, насколько машина быстрая, потому что дело в задержке, а не в CPU. `install.sh` ставит для этого [`mosh`](https://mosh.org): он отображает ваши нажатия локально и шлёт диффы экрана по UDP, так что печать мгновенна, а поток идёт гладко при любой задержке. Подключиться сразу в сессию:

```
mosh user@host -- omega attach -t claude-1
```

В клиенте вроде **Termius**: задайте IP и порт хоста, включите тумблер **mosh** и добавьте стартовый сниппет — `omega` для меню или `omega attach -t <session>`, чтобы попасть прямо в сессию.

(Для скроллбэка используйте `Alt+Up/Down` из rmux, а не PageUp из mosh.) Установщик ещё прописывает `/etc/rmux.conf` и UTF-8-локаль на всю систему, так что каждая учётная запись — root и будущие пользователи — получает ту же выверенную сессию (прокрутка мышью, выделение перетаскиванием в локальный буфер обмена по SSH, отзывчивые клавиши, truecolor) без настройки под каждого пользователя.

## Интеграция с Linear

Если вы ведёте пользовательский фидбэк в [Linear](https://linear.app), OmegaOS закрывает тикеты от начала до конца. Две команды.

`/omg-linear-setup` — одноразовый визард, который запускается внутри вашего собственного приложения. Он ставит встроенный виджет обратной связи (в момент отправки тот снимает скриншот, URL страницы, элемент, по которому кликнули, и консоль браузера), метки Linear, на которые опирается конвейер, и API-роут, превращающий репорт из виджета в issue Linear. Сначала он определяет ваш стек, провайдера аутентификации и UI-библиотеку, поэтому пишет код под проект, а не по общему шаблону.

`/omg-linear` делает работу. Он читает открытые тикеты и для каждого чинит код, снимает доказательства до и после, а затем прогоняет те аудиты Quality Arsenal, которые подходят к изменению. Тикет двигается дальше, только если эти аудиты дают 100/100. Потом он публикует в тикете комментарий с подтверждением фикса и переводит его в состояние ревью — `In Review`, если такое есть у вашей команды, иначе нейтральное `Omega Review`, которое создаёт сам. Он никогда не помечает тикет как Done; это после проверки делает человек. Движок v2 гоняет всё это через Workflow: сортирует открытые тикеты, раскидывает фикс и аудит по каждому тикету параллельно и состязательно проверяет каждое решение, прежде чем комментировать.

Он срабатывает только по триггеру. OmegaOS трогает Linear, только если вы позвали его по имени (`/omg-linear`, `fix linear`, id тикета вроде `KOM-7` или ссылка на `linear.app`). Голое слово «feedback» не запускает его никогда, и Linear он не упомянет, пока не упомянете вы.

```
omega_dir=~/.omega          # протокол ставится в ~/.omega/skills/linear/
/omg-linear-setup           # один раз на приложение — виджет + метки + роут
/omg-linear                 # закрыть открытые тикеты: фикс -> аудит -> коммент -> In Review
```

## Ограничения

Лучше вам знать о них заранее.

- **Linux в первую очередь.** Разрабатывалось на headless-VPS. Windows нет. На macOS есть настоящие фиксы (launchd-сервисы, путь Homebrew), но обкатки там заметно меньше.
- TUI рассчитан на терминал с 256 цветами. На 16-цветном будет уродливо.
- Среда исполнения агентов по умолчанию — OpenAI Codex, так что в CLI `codex` должен быть выполнен вход. Claude Code, Gemini, Pi, Hermes и GLM — поддерживаемые явные альтернативы.
- **Одна машина.** Демон rmux локален. Оркестрации между хостами нет.
- Это 0.1.x. Я пользуюсь этим каждый день, но вы найдёте шероховатости, на которые я ещё не натыкался.
